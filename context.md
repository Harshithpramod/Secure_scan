## 1. Project Identity

**What it does:** PentestAI connects to a user's GitHub repositories and runs
automated security analysis on them: an LLM statically reads a sample of files
(plus a deterministic regex pass for committed secrets), high/critical findings are
re-checked with real static analysis (CodeQL/Semgrep) inside a network-isolated
Docker sandbox to cut false positives, findings can be auto-patched by an LLM which
opens a GitHub PR (never a direct commit), repositories can be opted into weekly
re-scans with an emailed digest, and a chat assistant answers questions grounded in
the user's own scan data. A fully simulated `/demo` route needs no sign-in and
touches no real data.

**Target users:** developers / small security teams who want a fast, automated
first pass on their own GitHub repositories. The landing copy is explicit: *"Only
scan repositories you own or are explicitly authorised to test."*

**Business goals / success metrics:** not documented anywhere in the repo. No
analytics integration, no stated KPIs or growth targets exist in the code or docs —
this is a gap, not an oversight on this document's part.

**Project status:** **active development**, not a finished product. Signals:
- Git history is a single squashed commit (`efd54d3 Initial commit: PentestAI`) —
  no real history to read.
- `git status` (2026-10-13) shows **98 uncommitted paths**: 37 modified,
  6 deleted, 55 **untracked** (whole subsystems — chat, onboarding, weekly
  digest, the vulnerability lifecycle, the `fixer` sandbox service, the fix
  gate, most tests — exist on disk but were never committed).
- `ARCHITECTURE.md` and this `context.md` are themselves untracked.
- The project was scaffolded via **Lovable** (`@lovable.dev/vite-tanstack-config`
  devDependency, a `.claude/` directory with Claude Code settings, references to
  `src/integrations/lovable/index.ts` and `src/lib/lovable-error-reporting.ts` in
  the diff — both now **deleted** in the working tree, i.e. actively being
  de-Lovable'd) and has clearly since had substantial hand/AI-assisted
  engineering on top (the sandbox, verification pipeline, weekly digest, and the
  two long-form docs did not come from a page-builder).

**Practical implication for you:** commit the working tree. As it stands, a fresh
`git clone` of the pushed remote would be missing the entire sandbox `fixer/`
service, all the weekly-digest code, chat, onboarding, and nearly every test file.

## 3. Architecture & Design

### 3.1 Two independent halves over signed HTTP

```
App (TanStack Start, Node)                    Sandbox (Docker Compose)

routes/  -->  *.functions.ts                  caddy --> api (Fastify)
                   |                                       |
                   v                                       v
             sandbox.ts  ---- POST job ---------------->  redis (queue)
                                                            |
server.ts                                                  v
 /api/public/sandbox-callback   <---- HMAC callback ---  worker (persistent)
 /api/public/run-weekly-scans                              |
       |                                                    +-- scan.js (in-process)
       v                                                    +-- runner (one-shot, verify)
    Supabase  <---------------------------------------------+-- fixer  (one-shot, fix)
```

The app **never runs untrusted code**; the sandbox **never holds a database
credential**. Everything crossing the boundary is a signed HTTP message.

### 3.2 Why a separate sandbox

Cloning and statically analysing arbitrary user repositories is hostile input.
Doing that work in disposable, network-restricted containers means a malicious
repository cannot reach the app, the database, or the internet.

### 3.3 Docker network topology — **as documented**

| Network | `internal` | Members | Purpose |
| --- | --- | --- | --- |
| `edge` | no | caddy (public entry point) | |
| `internal` | yes | api, worker, redis | |
| `runner_net` | yes | verification runners | no outbound access at all |
| `fixer_net` | no | the fixer | needs egress to GitHub/OpenRouter |

`worker` is deliberately attached to `runner_net`/`fixer_net` even though it
doesn't use them directly, because Compose prunes networks nothing is attached
to — without that, the one-shot containers fail with "network not found".

✅ As of 2026-10-13 the compose file matches this: `fixer_net` is defined and the
worker carries the `FIXER_*` settings. Note the fixer and runner are **not**
Compose services — they are one-shot images (`pentestai/runner`,
`pentestai/fixer`) the worker starts with `docker run` per job, so they must be
built separately (§14.2).

### 3.4 Design patterns in use

- **Server-function / server-module split** (`*.functions.ts` vs `*.server.ts`) —
  the codebase's own convention, documented in `ARCHITECTURE.md` §3. `.functions.ts`
  files export `createServerFn(...)` values callable like async functions from
  React components (TanStack turns the call into an RPC); `.server.ts` files are
  never imported by a component, hold secrets, and are dynamically imported so they
  never reach the browser bundle.
- **Claim-before-act / idempotency locks** — the same pattern is reused three times:
  job IDs are generated by the *app* before a sandbox job is submitted (so a fast
  callback can never arrive before the row that should receive it exists), and
  `weekly_digest_log`'s `PRIMARY KEY (weekly_run_id, user_id)` is an idempotency
  lock — whoever inserts first wins the right to send the digest email, everyone
  else hits a unique-violation and silently skips.
- **Callback binding** — every sandbox callback handler matches on *both* the
  entity id and the job id the app itself issued (e.g.
  `.eq("id", vulnerability_id).eq("scan_id", scan_id).eq("sandbox_job_id", job_id)`),
  so a stray, replayed, or forged callback matches zero rows.
- **Security-definer RPC for role checks** — `has_role()` is `SECURITY DEFINER` so
  RLS policies on `user_roles` can call it without infinite recursion.
- **Degrade, don't fail, on missing schema** — every lifecycle/job-log code
  path (`vuln-lifecycle.server.ts`, `use-vuln-activity.ts`) detects that the
  `20260924…` migration hasn't been applied and falls back to the old
  behaviour, so a scan never fails because a timeline table is missing.
- **Pure core, thin I/O shell** — the rules that are easy to get wrong are kept
  in pure, unit-tested modules (`vuln-lifecycle.ts`, `activity-format.ts`,
  `worker/fix-gate.js`, `worker/job-stream.js`) with the database/Docker side in
  separate files.
- **Two-Supabase-client discipline** — an anon/RLS-respecting client for the
  browser, a service-role/RLS-bypassing admin client for the server, never mixed;
  every admin-client query manually filters by `user_id` since RLS isn't there to
  help.

### 3.5 High-level data flow

See §6.1 for the full scan lifecycle sequence — it is the central flow in the
system and is described end-to-end there rather than duplicated here.

### 3.6 Scalability / resilience posture

- The app is **stateless and request-driven**; the sandbox worker is the one
  long-running process and owns "what's due" scheduling via periodic HTTP pings
  rather than a cron on the app side (the app can't run one — see deploy target).
- Redis is explicitly **not** relied on for durability: "nothing retries a dropped
  job today, so surviving a Redis restart is not worth persisting credentials for"
  — and the compose file now actually runs it with `--appendonly no --save ""`.
- No load-testing, autoscaling config, or capacity planning exists in the repo —
  documented nowhere, presumably not yet a concern at this project's stage.

## 5. Data Model

Postgres via Supabase. **Every table has Row Level Security enabled**, standard
policy `auth.uid() = user_id` — enforced by Postgres, not application code.
Migrations live in `supabase/migrations/`, are applied **by hand** in filename
order (no established `supabase db push` history — README warns `db push` will
try to replay already-applied early migrations and fail).

· `repo_type` (web_app/api/library/mobile/infra/microservice) · `repo_status`

### Relationships

`repositories` → `auth.users` (many:1) → `scans` → `repositories`/`auth.users`
(many:1 each) → `vulnerabilities` → `scans` (`ON DELETE SET NULL`, so a finding
outlives the scan that produced it) and `repositories` (`ON DELETE CASCADE`) →
`scan_logs` → `scans` (`ON DELETE CASCADE`) → `reports` → `scans`/`repositories`.
`vulnerability_events` and `job_logs` → `vulnerabilities` (`ON DELETE CASCADE`);
`vulnerabilities.duplicate_of` → `vulnerabilities` (self-reference, `SET NULL`).
A trigger, `trg_vulnerability_status_event` (`SECURITY DEFINER`), writes a
`status_changed` event on every status change — manual (UI) or automatic
(reconciler), told apart by whether `status_reason` was set in the same UPDATE.

## 6. Core Features & Workflows

### 6.1 Scan lifecycle (the central flow — read this one fully)

1. **Trigger** — `startScan` (`scans.functions.ts`) authenticates the caller, then
   calls the shared `triggerScan()` in `scan-trigger.server.ts` (used by both the
   manual "Scan" button and the weekly sweep, so the two paths can't drift apart).
   It: loads the repo (checks ownership) → refuses if a scan is already
   queued/running for that repo → decrypts the user's GitHub token → **generates
   the job id itself** → inserts the `scans` row with that id already set → submits
   the job. Generating the id *before* submission is deliberate: if the sandbox
   assigned it, a fast job could finish and call back before the app had written
   the id anywhere, and the callback would match no row.
2. **Execution** (`sandbox/worker/scan.js`, in the worker process itself, no
   spawned container — a scan only reads text via the GitHub API and posts it to a
   model, there's no untrusted execution to isolate). Stages reported by percent:
   `fetch` (15–25%) → `select` (~35%) → `downloading` (45%) → `analyzing` (65%) →
   `persisting` (85%).
   - **File selection** (`pickScannable`) excludes `node_modules`/`dist`/`build`/
     `vendor`/`.git`/minified files/lockfiles **by path segment, not substring**
     (an earlier version's substring match on `"/dist/"` missed a top-level
     `dist/`, silently burning the file budget on generated bundles), then ranks
     the rest by how security-relevant the path looks, secret-bearing files first,
     capped at **18 files / 250 KB total**.
   - **Secret detection** (`scanForSecrets`) is pure regex and runs *before* the
     LLM, so a committed `.env` is caught deterministically even if the model
     misses it; `penalizeScore()` force-lowers the security score when secrets are
     present so the model can't "average it away."
   - **`sanitizeFindings()`** truncates/shape-checks model output before it
     touches the database.
3. **Callback** — `server.ts` intercepts `POST /api/public/sandbox-callback`
   *before* the router (no session — see §7). Verifies HMAC (constant-time
   compare) → 401 on mismatch → parses JSON → 400 on garbage → dispatches on
   `kind` (`scan_progress` / `scan` / `verify` / `fix` / `job_progress`, each
   bound to the exact row via id + job id — see §3.4; `kind` defaults to
   `verify` when absent).
4. **Persist** (`scan-results.server.ts`) — reconciles findings against the
   repository's existing rows (§6.10) instead of blindly inserting, updates scan
   counts/score, updates repo status, **then** submits verification jobs — in that
   order, deliberately: verification jobs must go out *before* the scan flips to
   `completed`, or the weekly digest could observe "all scans done, no
   verifications pending" in the gap between those two writes and send an
   incomplete digest.
5. **Live UI** — `scans.$scanId.tsx` subscribes to Supabase Realtime on
   `scan-logs-${scanId}`; log lines appear as the worker inserts rows, no polling.

### 6.2 Verification

High/critical findings each get a verification job; containers stream progress
lines to the live console as they go (§6.11). The `runner` container runs
with `--network none`, read-only root FS, hard `SIGKILL` timeout, and the git
credential stripped before untrusted code is mounted. `probe.sh` runs CodeQL
(building a language database) falling back to Semgrep; `sarif_verdict.py` maps
the probe category to expected CWEs so an SQLi probe can't be "confirmed" by an
unrelated XSS hit. Verdict is the last line of stdout, as JSON. Outcomes:
`confirmed` / `not_exploitable` / `failed` (kept distinct from a clean result —
"the scanner crashed" ≠ "the code is safe").

**Honest caveat (from the project's own docs):** despite the naming, this does
**not** verify exploitability. Nothing is executed. "Confirmed" means *two static
tools agreed*, not *proven exploitable*.

### 6.3 Fix with AI

`requestVulnerabilityFix` → the `fixer` container (one-shot image, launched by the
worker on `fixer_net`):

1. fetches the single affected file via the GitHub API (no clone — see §18), plus
   the surrounding files a real scan would read, and scans the **unpatched**
   repository twice (merged) to get a baseline;
2. asks a code model via OpenRouter (default `qwen/qwen3-coder`) for a patch;
3. **re-scans with the patch applied** using the scanner's own `analyzeFiles()`
   and compares finding-by-finding against the baseline (`worker/fix-gate.js`):
   the target finding must be gone and **no new medium+ finding** may appear in
   that file (a post-patch finding is "new" unless it pairs with a baseline
   finding at the same diff-mapped line or with a matching description);
4. a patch must pass **two** independent re-scans (the scanner is
   non-deterministic); on failure the model gets the re-scan's findings and
   retries, up to `FIX_MAX_ATTEMPTS` (default 3, clamped 1–5);
5. only a passing patch becomes a branch/commit/**pull request** — never a direct
   commit. If nothing passes, it fails with the reason and opens no PR.

A `pr_created` verdict with no URL is recorded as a **failure** on purpose. Only
one fix runs per finding at a time. Cost note from `.env.example`: each fix makes
2 scan calls up front plus up to 2 per attempt (8 max at 3 attempts) — relevant
on the Gemini free tier. The patch is **re-scanned, not compiled or executed**;
a human still has to review and test it.

### 6.4 Weekly scanning + digest

The app is request-driven with no cron of its own, so the sandbox worker (always
running) owns the clock: `scheduler.js` pings `/api/public/run-weekly-scans`
hourly (bearer-token auth, reusing `SANDBOX_API_TOKEN`). The **app**, not the
worker, decides what's due — comparing `repositories.last_scan_at` against
`WEEKLY_SWEEP_INTERVAL_HOURS` — because the sandbox's Redis is deliberately
non-persistent (a worker-side "last run" timestamp would be forgotten on
restart). Auto-scan is **opt-in per repository** (`scan_mode='weekly'`, off by
default). All scans from one sweep share a `weekly_run_id`.
`maybeSendWeeklyDigest()` runs after every scan/verification in a run, checks
every scan is terminal and nothing verification-pending, checks user
preferences, **claims** the send via the `weekly_digest_log` insert (23505 =
someone already won, skip), then emails.

### 6.5 Chat assistant

`chat.functions.ts` + `chat-context.server.ts` build a context bundle from the
user's own scan data, sent through `ai-gateway.server.ts` to Gemini via its
OpenAI-compatible endpoint (chosen so the request shape is portable to any
OpenAI-style provider later). Widget (`chat-widget.tsx`) is a draggable orb that
only moves once dragged.

### 6.6 Onboarding

`onboarding.functions.ts` tracks `profiles.onboarding_completed` (see migration
#5); `onboarding-tour.tsx` renders the guided tour. Deliberately stored server-side
rather than in `localStorage` so it doesn't re-trigger per-browser or reset when
storage is cleared.

### 6.7 Reports

`reports.functions.ts` generates and stores report payloads. **JSON format only**
today — `reports.format` defaults to `'pdf'` in the schema but nothing produces a
PDF yet (a real gap between the column default and actual behavior).

### 6.8 Demo mode (`/demo`)

Fully simulated, reads only from static `lib/demo-data.ts`. No Supabase client,
no server function, and no `fetch` is imported anywhere in that subtree — the
project's own docs state this was verified, not assumed, so no interaction can
touch real data. Deliberately **not** nested under the authenticated route guard.

### 6.9 Landing page

`index.tsx` — a `ColorBends` WebGL shader (vendored from React Bits), a CSS mask
standing in for an upstream prop, `prefers-reduced-motion` bypassing WebGL
entirely for a static gradient. See §11/§19 for the accessibility work done here.

### 6.10 Vulnerability lifecycle

A finding is one row for its whole life. `persistScanResults` reconciles each
scan against the repository's existing rows using the pure rules in
`vuln-lifecycle.ts` (DB side in `vuln-lifecycle.server.ts`):

| Situation | Effect |
| --- | --- |
| Reported finding matches an existing row | row updated (`last_seen_*`), `seen` event |
| No match | new row, `detected` event |
| Matches a `fixed` row | reopened as a **regression** (`regression_count`++) and re-verified |
| Matches a `false_positive` row | stays triaged |
| Active row not reported, and the scan **read its file** | `missed_scans`++; resolved after **two consecutive misses**, after **one** if its AI-fix PR was merged, immediately if the file was deleted |
| Active row not reported, file not read | nothing — the scan only samples ~18 files, so absence isn't evidence |
| Two rows are the same issue (e.g. CWE-312 vs CWE-256 for one bug) | the extra gets `duplicate_of` and is hidden, history kept |

"Same issue" is decided by file, location and description similarity, because
the LLM rewords titles and relabels CWEs between runs — see §16.1. Reports and
the weekly digest now count findings **present in** a scan (first seen, last
seen, or recorded as seen), not just `scan_id`. The UI shows this as a timeline
(`vuln-timeline.tsx`).

### 6.11 Live sandbox console

Verify and fix containers write `@@progress {json}` lines to stderr. The worker
(`job-stream.js`) relays **only** those marked lines — never raw tool output
about untrusted code — redacts secret-shaped values (the scanner's secret
patterns plus quoted/env-style credential assignments), caps each job at 300
lines, and sends each as a signed `job_progress` callback carrying a monotonic
`seq`. The app binds each line to the job the finding currently owns and stores
it in `job_logs`. The finding dialog (`sandbox-console.tsx`, via
`use-vuln-activity.ts`) streams it over Realtime with polling as a fallback,
showing the container's real isolation settings, each fix attempt's diff, and
what each re-scan said. `/demo` replays a recorded run (`demo-fix-run.ts`) in the
same shape.

## 7. API / Interface Layer

There is **no conventional REST/OpenAPI surface** for the main app. Almost all
client↔server calls are **TanStack server functions** — plain async function
calls from React that TanStack turns into RPCs under the hood, not endpoints you'd
call from `curl`. The only two raw HTTP endpoints are intercepted directly in
`src/server.ts` before the router even runs.

### 7.1 Raw HTTP endpoints (app)

| Route | Method | Auth | Handler | Purpose |
| --- | --- | --- | --- | --- |
| `/api/public/sandbox-callback` | POST | **HMAC-SHA256** signature (`CALLBACK_HMAC_SECRET`), `timingSafeEqual` compare, no user session | `sandbox-callback.server.ts` → `handleSandboxCallback` | Sandbox → app delivery for scan/verify/fix results and `scan_progress`/`job_progress` lines (see §6.1 step 3) |
| `/api/public/run-weekly-scans` | POST | Bearer token = `SANDBOX_API_TOKEN` | `weekly-scan-sweep.server.ts` → `handleWeeklySweepRequest` | Sandbox worker pings this hourly; app decides what's due |

Both return whatever status the handler determines (401 on bad HMAC, 400 on
malformed JSON or missing fields, 500 on an unexpected error — which the worker
retries, §12) — no formal error-response schema or OpenAPI/Swagger doc exists.
**No API versioning strategy** — these are internal, single-consumer endpoints.
**No rate limiting** on either — see §11/§16.

Grouped by module, method as declared in `createServerFn({ method })`:

Every one of these runs through `attachSupabaseAuth` (the global `functionMiddleware`

always supplies it). A `GET /api/health` route also exists (used in the deploy
smoke test in `sandbox/README.md`). This API is not meant to be public-facing
beyond the one app instance that holds its token.

## 10. Authentication & Authorization

### 10.1 Sign-in

GitHub OAuth via Supabase Auth. `_authenticated/route.tsx`'s `beforeLoad` redirects
signed-out visitors to `/auth`. `/demo` is deliberately **not** nested under that
guard, which is why it works with no account.

### 10.2 Roles

`app_role` enum: `admin` / `pentester` / `developer`. Every new signup gets
`developer` by default via the `handle_new_user()` trigger. `has_role(user_id, role)`
is a `SECURITY DEFINER` SQL function used inside RLS policies (e.g. "Admins view
all X") specifically so checking a role doesn't recurse back into `user_roles`'
own RLS. **No UI for assigning `admin`/`pentester` was found in the routes
explored** — role changes likely require a direct DB write today (a gap worth
confirming with whoever set up the first admin account).

### 10.3 Session / token management

Standard Supabase JWT session handling (`@supabase/supabase-js`), resolved
per-request server-side via `requireSupabaseAuth` / `attachSupabaseAuth`
middleware so a server function always knows who's calling. No custom session
expiry configuration was found beyond Supabase's defaults.

### 10.4 Access control enforcement

**Two layers, deliberately not just one:**
1. **Postgres RLS** — `auth.uid() = user_id` on almost every table; the true
   enforcement boundary.
2. **Application-level filtering** — the service-role admin client bypasses RLS
   entirely, so every admin-client query in `*.server.ts` files must manually
   filter by `user_id` itself. This is a real trust boundary a future contributor
   could break by adding a new admin-client query without the filter — worth a
   lint rule or code-review checklist item, since nothing currently enforces it
   automatically.

### 10.5 GitHub tokens — the encryption-at-rest design

`token-crypto.server.ts`: AES-256-GCM via WebCrypto, stored as
`v1.<iv>.<ciphertext>` — the version prefix future-proofs key rotation.
`isEncryptedToken()` detects legacy plaintext rows; `getUserAccessToken()`
transparently re-encrypts them on read, so migration is gradual with **no
downtime and no migration script** needed.

### 10.6 GitHub tokens in transit

Never interpolated into a clone URL (`https://<token>@github.com/...` leaks into
`.git/config`, `ps` output, and error messages). `worker.js` instead uses a git
credential helper reading the token from an environment variable — never in
`argv`, never written to `.git/config`; the credential is stripped before the
prepared repo is mounted into the (untrusted-code-executing) runner.

### 10.7 Password policy / MFA

Not applicable — auth is GitHub OAuth only (plus what looks like an optional PAT
path, `connectGithubPat`, for users who prefer a personal access token over
OAuth). No separate PentestAI password exists to have a policy on. No MFA layer
beyond whatever the user's own GitHub account enforces.

## 11. Performance & Optimization

- **Caching:** No explicit CDN/edge-cache config found beyond whatever Cloudflare
  Workers provides by default for the Nitro build. TanStack Query provides
  client-side data caching for reads. No Redis-as-app-cache — the sandbox's Redis
  is a job queue only, not shared with the main app.
- **Database:** Indexes are deliberate and documented (see §5) — most are partial
  indexes scoped to the exact query pattern they support (e.g.
  `idx_scans_active_by_repo WHERE status IN ('queued','running')` for the
  duplicate-scan check). No slow-query analysis or query-plan documentation
  exists in the repo.
- **Code-level:** File-selection budgeting (18 files / 250 KB per scan — see §6.1)
  is itself a performance/cost control, not just a scan-quality one — it bounds
  both LLM token spend and scan latency.
- **Landing-page motion policy** (`docs/DESIGN-SYSTEM.md`) is explicitly written
  as a performance/UX correction: the *previous* implementation ran "12+
  concurrent animation groups" and was rewritten to `opacity`/`transform`-only,
  one-shot-on-enter animations, because it's flagged as a **High severity** issue
  by the design tooling used ("Excessive Motion").
- **Load testing:** none found — no k6/Artillery/locust config, no documented
  targets.
- **Known bottleneck (self-documented):** CodeQL verification needs materially
  more CPU/RAM/time than the semgrep-only approach it replaced — `RUNNER_CPU`
  (2.0), `RUNNER_MEMORY` (3g), `RUNNER_TMPFS_SIZE` (2g), `RUNNER_TIMEOUT_SECONDS`
  (1200) in `docker-compose.yml` reflect that; `RUNNER_TMPFS_SIZE` backs the
  runner's `$HOME` (CodeQL DB + caches) and must stay comfortably under
  `RUNNER_MEMORY` or the container gets OOM-killed mid-analysis.

## 12. Error Handling & Logging

- **SSR error wrapping** (`src/server.ts`): h3 (TanStack Start's underlying
  server) swallows in-handler throws into an opaque
  `{"unhandled":true,"message":"HTTPError"}` 500 that a normal `try/catch` never
  sees. `normalizeCatastrophicSsrResponse()` specifically detects that JSON shape
  and substitutes a real rendered error page (`error-page.ts`), logging the
  original error via `consumeLastCapturedError()` (`error-capture.ts`) first.
- **Middleware-level error handling** (`src/start.ts`): a global `errorMiddleware`
  re-throws anything that already looks like an HTTP error (`statusCode` present)
  and otherwise logs + returns the same rendered error page.
- **Logging:** plain `console.error` throughout — **no structured logging
  framework** (pino/winston), **no external log aggregation**, and **no error
  tracking service** (no Sentry or equivalent found in dependencies or code).
  This is a real observability gap for a security product: if the sandbox worker
  crashes mid-job in production, the operator's only signal today is whatever
  reaches stdout on that container.
- **Sandbox-side:** `worker.js`'s `postCallback()` now logs every non-2xx and
  retries **final results** on network errors and 5xx, with linear backoff
  (2 s, 4 s, …). A 4xx is not retried (the app has said the payload is wrong).
  There is still no durable outbox: if the app is down longer than the retries,
  the result is lost and the row stays `queued`/`running` (see §16.1).
- **Monitoring/alerting/alert thresholds:** none configured — no
  uptime/health-check monitoring, no PagerDuty/Opsgenie integration found.
  `GET /api/health` exists on the sandbox API but nothing is wired to poll it.

## 16. Known Issues & Limitations

These fall into two groups: issues **the project's own docs already state**
(reproduced here so they're in one place), and issues **found by reading the
actual code/config during this analysis** that aren't mentioned in the docs.

### 16.1 Self-documented (from `ARCHITECTURE.md` §12 and `README.md`)

- **Scan coverage is narrow.** At most 18 files / 250 KB read by an LLM; results
  are not deterministic — the same commit scanned twice can differ. CodeQL/Semgrep
  are installed in the runner image but **not used during the scan step itself**
  (only during verification).
- **"Verification" doesn't prove exploitability.** `--network none`, nothing
  executed; "confirmed" means two static tools agreed on a CWE, not that the bug
  was demonstrated live.
- **Callback delivery is best-effort.** This used to be fire-and-forget (a
  rejected result vanished and its row sat in `queued` forever — **it happened in
  practice**). Now non-2xx is logged and final results are retried 3× on
  network/5xx errors, but there is no durable outbox, so a long app outage
  still loses results.
- **Finding identity across scans is heuristic.** Matching is by file, location
  and description similarity, so two different issues at one spot with similar
  titles can merge, and a heavily reworded one can show as new.
- **Dropped jobs are never retried.** A worker restart mid-job abandons that scan
  in `running` state permanently.
- **AI fixes are re-scanned, not tested.** A PR opens only if two re-scans with
  the patch applied pass the fix gate, but nothing is compiled or executed, and
  the AI re-scan can pass an unchanged patch on one run and fail it on the next.
- **Email needs a real TCP socket** (nodemailer/SMTP) — works today because the
  app runs as a persistent Node process, but would break on genuine serverless
  Cloudflare Workers (no raw sockets). Contained to `email.server.ts` if it ever
  needs fixing.
- **Weekly scheduling is coarse** — rolling "every N hours since last scan" only;
  `schedule_day`/`schedule_hour`/`timezone` columns exist but are unwired.
- **Caddy needs real DNS** before it can issue a TLS cert — not usable "out of
  the box" on a fresh VPS without that step.
- **Test coverage is targeted, not broad** (see §13).

## 19. Security

This is a security-tooling product, so it's worth summarizing the security design
distinctly from the general architecture notes above (most detail already lives
in §3, §5, §6, §10 — this section indexes it plus adds what's specific to §19).

- **Data encryption at rest:** GitHub tokens only, AES-256-GCM (§10.5). **Nothing
  else in the database is application-level encrypted** — findings, scan content,
  etc. rely on Supabase/Postgres's own at-rest encryption, not a project-level
  scheme.
- **Data encryption in transit:** Supabase connections are TLS by default; sandbox
  callbacks travel over plain HTTP but are HMAC-signed (not encrypted — signed
  for integrity/authenticity, not confidentiality) — worth noting the callback
  channel itself should still sit behind TLS in production (Caddy provides that
  for the sandbox's public side).
- **Input validation / sanitization:** `sanitizeFindings()` shape-checks/truncates
  LLM output before it reaches the database (§6.1) — the project explicitly
  treats **model output as untrusted input**, which is a good practice that's
  easy to skip in AI-adjacent codebases. Zod is used for schema validation in the
  sandbox API (`sandbox/api` dependency).
- **CORS / security headers:** not explicitly configured anywhere found in this
  analysis (no CORS middleware, no CSP/security-headers config) — likely relies
  on Cloudflare Workers/Nitro defaults; worth an explicit audit before
  production.
- **SQL injection:** mitigated structurally — all app↔DB access goes through the
  Supabase client library (parameterized), not raw SQL string building.
- **XSS:** React's default JSX escaping is the primary defense; `chat-markdown.tsx`
  renders LLM output as markdown, which is the one place worth double-checking
  for a sanitizer (e.g. `rehype-sanitize` or equivalent) since it's rendering
  AI-generated content — not confirmed one way or the other in this pass.
- **CSRF:** explicit `createCsrfMiddleware` applied to all server-function
  requests (`src/start.ts`) — deliberately re-added since TanStack Start would
  otherwise install it automatically only when `src/start.ts` is *absent*.
- **Compliance requirements (GDPR/HIPAA/SOC2):** **none found** — no privacy
  policy, no data-processing agreement template, no compliance-related code
  (no data-export/right-to-erasure endpoint, no consent-logging beyond the one
  `profiles.authorization_ack` boolean, which appears to record "I'm authorized
  to scan this repo," not a privacy consent). See §22.
- **Security audit logs:** `scan_logs` records scan progress, not an audit trail
  of *user actions* (who connected what, who requested a fix, etc.) — there's no
  dedicated audit-log table.
- **Vulnerability disclosure policy:** none found (no `SECURITY.md`).
- **Untrusted output kept out of the UI:** the live console relays only lines
  the containers deliberately emit (never raw tool output about the scanned
  code) and redacts secret-shaped values first (§6.11). `chat-markdown.tsx`
  renders the assistant's markdown to React elements itself and never uses
  `dangerouslySetInnerHTML` (stated in the file's header comment), which
  answers the XSS question raised above.
- **The sandbox's own security posture is unusually well-engineered** — see §3.3
  and §14.3. The two sandbox gaps flagged in the first pass (missing `fixer`
  wiring, Redis persisting credentials) are now fixed (§16.2).
